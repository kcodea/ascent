## What was built

- **Catalog (code-owned) + SQL** (`packages/progression/src/cosmetics.ts`,
  `supabase/migrations/2026-09-28-progression-skins.sql`, appended to `schema.sql`). `hero_skin` + `minion_skin`
  switched on and four items, in CODE. The migration seeds no catalog rows at all: it adds
  `sync_cosmetic_catalog(catalog, hash)` (service role only, one global lock, one transaction), `admin_off` on both
  catalog tables, `progression_config.catalog_hash`, `equip_cosmetic(user, slot, target_id, cosmetic_id)` (same
  per-user lock; checks slot, target, effective liveness, ownership; null = Default), and redefines the crate pool
  and `progression_profile_json` (now also `cosmetics` and a live-only `loadout`) on the EFFECTIVE state
  (`active AND NOT admin_off`, `enabled AND NOT admin_off`). The crates file's seeds became `on conflict do
  nothing`, so re-running it can never flip a flag. Everything runs on PGlite in CI (`skins.db.test.ts`).
- **The catalog sync** (owner ruling above). `catalogSyncPayload()` + `catalogHash()` in `cosmetics.ts`;
  `syncCatalogOnce` in `inventory.ts` (generated into `supabase/functions/_shared/`); the `progression-inventory`
  entry point awaits it once per cold start, before the auth check (so the anon 401 probe triggers it). It never
  throws; a failure is logged and retried after 60 s. Items in code are upserted; an item REMOVED from code is marked
  `active = false`, never deleted; `admin_off` is never written. An unchanged hash is one read.
- **The inventory Edge Function** gains `{ action: 'equip_cosmetic', slot, targetId, cosmeticId }`
  (`packages/progression/src/inventory.ts`, regenerated into `supabase/functions/_shared/`).
- **One resolver for every renderer.** `isCosmeticLive` / `heroSkinOf` / `minionSkinOf` (@game/progression) return a
  skin only when it is live and made for THAT hero / card. `packages/ui/src/skins/` turns a snapshot into a
  `cardId -> art` map once (cached per snapshot CONTENT + catalog epoch, because the reducer clones the run on every
  dispatch) and hands it to `Card` through context, so
  `Unit`'s memo comparator is untouched and the context value is referentially stable. Hero portraits go through
  `heroPortrait(heroId, snapshot)`.
- **Recorded per run** (handoff §5.6). `RunState.cosmetics` is stamped from the live loadout when a run starts
  (`recordRunCosmetics` in `store.ts`; mid-run equips apply to the next run). `snapshotBoard` scopes it onto every
  captured `BoardSnapshot.cosmetics` (hero + the cards on that board); a replayed non-lobby run gets it stamped back
  in `saveRunBoards`. `playerRunsFrom` unions a run's boards and `createRunLobby` copies it onto the snapshot seat
  (`LobbySeatState.cosmetics`). Replay v2 shop frames carry both automatically (new RunState keys are captured by
  default; a delta never re-sends them).
- **Surfaces.** Hero skins: hero select + the pick ceremony (live loadout), your portrait / the combat hero
  (StatusBar), the seat list (yours and theirs), the combat opponent portrait, NOW FACING, the fight recap, the
  (non-lobby) end screen, the non-lobby opponent frame, the Career favourite hero, match-history rows and hero tiles.
  Minion skins: every `Card` inside `Game.tsx`'s own-skins scope (shop, hand, board, your combat row, Discover, Choose
  One, drag ghosts, cast preview, end screen boards, the Minion Book), the enemy combat row and the scouted board

- **Show opponent skins** (Esc menu, new "Skins" section, on by default, `localStorage['ascent.showopponentskins']`).

## Judgement calls (flag if wrong)

1. **Retired items are HIDDEN in the Collection** (owned or not), not shown as "owned but retired". A removal is
   usually made because the item must not be seen any more; ownership and the loadout row stay on the server, so a
   restore brings it back owned and still equipped.
2. **The loadout is locked in when a run starts.** Equipping mid-run changes the next run. It keeps what you see and
   what opponents / replays see identical.
3. **Skins are recorded even when retired later.** Boards store the id; the renderer decides. So a restore brings a
   skin back on old boards too.
4. **The client also reads the server's switches** (`active` / `enabled` and `admin_off`, all public) at boot and
   caches the answer, so a retire works on already-shipped clients. The server can only remove; it can never make an
   unknown id live. A new item in code shows in the Collection as soon as that build ships, even before the deploy
   syncs it; it just cannot drop or be equipped until then.
5. **Only `progression-inventory` syncs.** `submit-progression` bundles the same catalog but does not sync: two
   functions deployed at different times would carry different catalogs and push them over each other on every cold
   start (an older one would re-deactivate a skin you just added). One writer, one deploy command.
6. **Re-running files.** The skins file is safe to re-run any time (it writes no flags and clears the hash, so the
   next cold start re-syncs). The crates file's seeds no longer overwrite anything, but it does redefine the crate
   pool and the profile JSON without the emergency switch, so if it is ever re-run, re-run the skins file after it.
7. **The emergency switch is `admin_off`, not `active`.** `active` belongs to code now (the sync writes it); the
   owner's one-liners set `admin_off`, which the sync never touches, so the next deploy cannot silently undo them.
   Titles honour it in the crate pool; a retired TITLE that someone already wears still shows (titles were not in
   the render fallback brief).
8. **Recorded skins are client-stamped** (like `author` / `patch`). A forged payload can only name skins that exist
   and only for their own target; it unlocks nothing. Server-side verification of a snapshot against ownership is a
   possible follow-up.
9. **Not covered:** leaderboard / Rankings / Recent Games team strips and portraits (`LadderBits`) and the Minion
   Book's hero catalogue show default art. They were not in the brief, and leaderboard rows mix your own row with
   others'.
10. **Crate odds moved.** Category weights (hero 20, minion 35, title 10) are the handoff's. A fresh account's first
   crate is now about a 25.8% skin (Common 50.9%, Rare 33.7%, Epic 15.1%, Legendary 0.4%).
11. **Collection tab order** follows the handoff (Heroes, Minions, Titles), but the page still lands on Titles.

### How to add a cosmetic from now on (no SQL; owner ruling "make it automated when i add skins")

1. Master into `C:/Game Assets/Ascent Art/Skins/<Hero Skins|Minion Skins>/`.
2. An entry in `COSMETICS` in `packages/progression/src/cosmetics.ts` (new permanent id, name, rarity, target hero or
   card id, `assets.master` = the master filename).
3. `npm run art:wire -- --only=skins --apply`, then `npm run optimize-art`.
4. `npm run progression:shared`.
5. Merge, then `npx supabase functions deploy progression-inventory --project-ref zcwhbejpqcdcfdpfxeza`.
6. Probe: POST the function once (as in step 4 above), then
   `curl "https://zcwhbejpqcdcfdpfxeza.supabase.co/rest/v1/cosmetic_catalog?select=cosmetic_id,active,admin_off&cosmetic_id=eq.<id>" -H "apikey: <anon-key>"`
   answers `[{"cosmetic_id":"<id>","active":true,"admin_off":false}]`.

A permanent retire is `active: false` on the item in the same file (or removing the entry: the database marks it
inactive, never deletes it), then steps 4 and 5.

### The emergency switch (one line each; paste in the SQL Editor; no deploy needed)

```sql
-- retire one item (leaves the crate pool, cannot be equipped, drops out of every loadout, hidden in the Collection,
-- default art everywhere, even on old boards / replays that name it)
update public.cosmetic_catalog set admin_off = true where cosmetic_id = 'skin_blackbelt_2';
-- retire a whole category
update public.cosmetic_categories set admin_off = true, updated_at = now() where category = 'minion_skin';
-- restore (ownership and loadout rows were never deleted, so it comes back owned and still equipped)
update public.cosmetic_catalog set admin_off = false where cosmetic_id = 'skin_blackbelt_2';
update public.cosmetic_categories set admin_off = false, updated_at = now() where category = 'minion_skin';
```

`admin_off` is a separate column the deploy sync never writes, so the next deploy cannot undo an emergency retire.
Clients pick a switch up on their next boot (the probe runs at sign-in).
