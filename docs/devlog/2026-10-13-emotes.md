# 2026-10-13 — Emotes: a four-slot menu on your portrait, recorded and replayed in the snapshot lobby

Owner spec (2026-10-13): *"Players right-click THEIR hero's portrait (in game) to open an emote menu showing their 4
equipped emotes; clicking one plays it."*, *"Cooldown: 20 seconds between emotes ... No per-turn cap. No muting for
now."*, *"Emotes are a new COSMETIC type in Collections ... Unlock source: crates, plus starter emotes everyone owns."*,
and for the lobby: *"record each emote the player uses with its time offset ... when that recorded seat is served to
other players, replay the emote at that same offset beside that seat's rail portrait"*. Oracle rules
`R-PROG-EMOTE-01` (the cosmetic, the menu, the cooldown) and `R-EMOTE-01` (the snapshot contract).

## OWNER RUNBOOK (after this PR merges, in this order)

The game works without any of this: the menu, the bubbles and the recording need no server change, and a Collection
slot change is kept on the device until the server takes it. These steps make the Collection's slot changes follow the
account.

1. **SQL first.** Paste `supabase/migrations/2026-10-13-emotes.sql` into the Supabase SQL Editor and Run. It widens the
   `cosmetic_catalog.acquisition_source` check to allow `'starter'` and replaces `equip_cosmetic` (adds the `emote`
   slot). It writes no rows and is safe to re-run.
2. **Then deploy the function** (its catalog adds the Emotes category and the four starter emotes):
   `npx supabase functions deploy progression-inventory --project-ref zcwhbejpqcdcfdpfxeza`
   **Order matters.** Deployed before step 1, the catalog sync is refused by the old check (the starter emotes), logs
   `catalog sync failed`, and retries once a minute: nothing breaks for players, but NO catalog change (this one or any
   other cosmetic added since) reaches the database until step 1 runs. Running step 1 afterwards fixes it on the next
   retry, no redeploy needed.
3. **Verify** (read-only anon REST, after any one Collection visit or crate open so the function has cold-started):
   - `GET /rest/v1/cosmetic_categories?category=eq.emote&select=enabled,target` returns
     `[{"enabled":true,"target":"global"}]`.
   - `GET /rest/v1/cosmetic_catalog?category=eq.emote&select=cosmetic_id,acquisition_source,active&order=cosmetic_id`
     returns the four starters, each `"acquisition_source":"starter","active":true`: `emote_angry_mushy`,
     `emote_flirty_midas`, `emote_nervous_jensen`, `emote_zen_brian`. (Rows here prove both steps: the sync could only
     write them after the new check.)
   - In game: Collection > Emotes > pick Zen Brian > Slot 1, reload the page signed in: the menu still opens with Zen
     Brian first (served by the account, not the device).

No SQL is needed for the recorded emotes: they ride each board inside `boards.snapshot` (jsonb, stored and served
verbatim by `pool_runs_sample`).

## What shipped

- **The catalog** (`packages/progression/src/cosmetics.ts`). A new `emote` category (Emotes, global, on) and a new
  acquisition, `starter`: owned by every player from the start (signed in or not), no ownership row, never in the crate
  pool. The four painted bubbles in `C:\Game Assets\Ascent Art\Emotes\` are the starters (EmoteTemplate.png is the
  template and is not wired). A crate emote needs nothing new: add it with `acquisition: { type: 'crate' }`.
- **The menu loadout.** Four positions, one `cosmetic_loadouts` row each (`slot 'emote'`, `target_id '0'..'3'`).
  `emoteLoadoutOf` reads explicit positions first, then fills each gap with its own starter, else the starter pushed out
  of its position (so putting a starter elsewhere SWAPS), else any starter not shown. The SQL moves an emote (it leaves
  its other position). `ui/src/emotes/emoteLoadout.ts` lays a device copy over the account's rows when the server cannot
  take an equip (signed out, offline, SQL not run), so the feature always works.
- **In a game** (`ui/src/emotes/`). Right-click YOUR portrait (`StatusBar.tsx`, the `.f` disc: the browser menu is
  suppressed there only; the left click still opens Buffs and the hero power button is untouched). The menu (an `.atip`
  plate, portaled to the stage host) shows your four; pick one and its bubble pops beside your portrait. 20 s between
  emotes, shown on the menu as "Ready in Ns" plus a one-shot bar; no cap; nothing in a replay.
- **The bubble** (`emoteBubble.ts`): one `<img>` on the stage host, placed from ONE rect read, WAAPI transform +
  opacity, about 3.2 s, removed on finish. Nothing loops. One bubble per seat at a time.
- **Recording** (`emoteRecording.ts` + one line in `store.ts`). Each emote records `{ id, phase, at }` where `at` is ms
  into the phase (shop turn = the run entering `recruit` for the wave; combat = the run entering `combat`). A shop emote
  is held until the round's board is captured (`faceOmen`), a combat emote lands on the already-captured board. Lobby
  runs only. `snapshotBoard` never writes it (still pure).
- **Replay of served seats** (`EmoteLayer.tsx` + `seatEmoteSchedule` in `runLobby.ts`). At each phase start, every
  standing seat driven by a REAL player's recording (`SeatDriver.realPlayer`, set only by `snapshotSeat`) schedules
  that round's emotes of that phase at the same offset into your phase. Bots, hybrids and authored seats are never asked
  for a board. A recording served past its end stays quiet. An emote whose moment passed is dropped (never played late).
- **The transport seam** (`emoteTransport.ts`): `EmoteMessage { emoteId, seat, phase, offsetMs, round }`, `sendEmote`,
  `deliverEmote`, `subscribeEmotes`, `setEmoteTransport`. Today a local loopback. Versus later installs a Realtime
  transport whose `send` broadcasts and whose incoming messages call `deliverEmote`. Nothing else changes.
- **Collection**: an Emotes tab (tiles show the bubble), the detail panel previews the bubble and offers Slot 1 to 4.
  The four starters count as owned for everyone, so the header total moved by four (e.g. "2 / 229" is now "6 / 233").

## Judgement calls (flag to the owner)

- **Bubble placement and the baked-in tail.** The tail points down-left, so the art reads right up and to the RIGHT of
  the speaker. Your portrait is bottom-left: your bubble rises from its top-right, as painted. The rail (right edge) and
  the combat foe (top-right) have no room on the right, so their bubbles open to the LEFT, MIRRORED so the tail still
  points at the face. The art has no lettering, so the mirror reads fine; a painted left-facing variant could replace
  it.
- **Combat.** The rail slides away in combat, so another seat's combat emote shows only when that seat is the foe you
  are fighting (beside its combat portrait). Other seats' combat emotes are not shown.
- **Two masters had no transparency.** NervousJensen.png and ZenBrian.png are opaque on black. The shipped webps key the
  black out (a flood fill from the border with a soft edge); the masters are untouched. Re-exporting them with alpha
  would be cleaner.
- **"Show opponent cosmetics" does not hide emotes** ("No muting for now"). Say if it should.
- **Practice / tutorial / Gauntlet / sandbox**: you can emote, nothing is recorded (only rated lobby boards upload).

## Limits

- A shop emote said, then a save-and-resume before the turn ends, is lost (held in memory). Combat emotes ride the saved
  boards.
- Replay v2 does not carry emotes (not cheap: per-round draft chunks, resume offsets and the viewer would all need it).
- The emote is recorded in the PLAYER's time; a served seat in a shorter turn simply never reaches a late emote.
