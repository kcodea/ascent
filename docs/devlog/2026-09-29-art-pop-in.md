# 2026-09-29 — Art pop-in: an ordered asset pipe, never-undecoded images, Netlify cache headers

Owner report: *"seeing a lot of pop in when i watch my friends play when they roll into a fresh shop etc. how can
we stop pop in entirely?"*, then: *"i dont think it's just a netlify issue - mike's has pop in sometimes too and i
rarely do as well"*. Both are true, and they have different causes. Both are fixed here.

## How it was measured

- **Remote friend (throttled):** the prod build (`npm run build:web`) served by a small Node server that behaves
  like Netlify: no `_headers` → `Cache-Control: public, max-age=0, must-revalidate` + ETag + 304s, gzip on text,
  one shared bandwidth cap and per-request latency (10 Mbps / 60 ms, and a slow 4 Mbps / 120 ms line). Headless
  Chrome over CDP, 1920×1080, fresh profile = first visit, same profile again = returning visit.
- **Local (unthrottled):** `vite preview` of the prod build and the Vite dev server, each against a detached
  `origin/main` worktree for "before".
- **Scenario:** boot → title → Play → skip tutorial → first hero → Start → first shop (6 s) → Refresh → Refresh.
  The local scenario also lets the turn run out, plays the combat and rolls twice more in shop 2.
- **Probe (every frame, from document start):** for every visible `<img>` inside a card or combat unit, and
  separately for every other visible `<img>` (portraits, buttons, tiles): is it in the DOM but not yet
  loadable (`complete && naturalWidth`)? That is a frame the player sees a card with a hole where its art or
  frame should be. Frames where the art is deliberately hidden behind the new placeholder are counted apart.
  Also recorded: time from a card's first frame to its art, rAF frame times, long tasks, bytes and requests
  on the server, renderer memory (Windows working set / private bytes, after a forced GC).

## What "pop in" was

**1. Network ORDER (friends on Netlify).** The old warm-up (`preloadAllArt` in Boot + `warmArt` in Game) fired
~650 image requests at once, in alphabetical order, and the first click fired ~430 SFX fetches on top. On a
10 Mbps line the tier-1 card on screen waited behind the whole bundle: the first shop showed **blank white
ovals with no frames for 6.9 s** (1,558 of 1,628 frames), and each roll showed blank cards for 1-2.4 s. Hero
select showed empty portrait boxes and the mode picker empty tiles. Worse, the warm-up never covered spells,
card frames and plates, tier stars, shop buttons, medallions, runes, quests, equipment, skins or mode tiles,
so those were fetched only when they first appeared.

**2. No cache headers (returning friends).** With Netlify's default `max-age=0, must-revalidate`, a returning
visit re-asked the server about every image before using its own copy: **722 revalidation requests** in one
warm visit, and still 41-80 blank frames per shop / roll (each 304 round trip queued behind hundreds of others).

**3. Local, no network at all (Mike, Kevin).** Two non-network causes, both measured on localhost:
- **First appearance of art the warm-up never touched.** Even from localhost an image load is asynchronous:
  a new `<img>` whose URL is not in the page's memory cache paints its first frame(s) empty. Before: the mode
  tiles were blank for 100-170 frames, the first shop had 1-3 blank frames, and each first roll 3-4 (frames,
  medallions, milestone discs, spell frames: none of them were preloaded).
- **A new `<img>` element can revalidate even when the URL is already loaded.** The Vite dev server and
  `vite preview` answer every file `Cache-Control: no-cache`. Resource timing showed a brand-new card `<img>`
  (and the spell frame, which a CSS rule also loads) issuing a fresh 304 request on a roll: that element is
  async and paints blank until the 304 lands, even though the preloader had decoded the same URL seconds
  earlier. This is the "sometimes": it depends on which URLs the document has already revalidated.

`decoding="sync"` (already on every game `<img>`, see `imgDecodingSync.test.ts`) prevents the DECODE half of a
pop (the compositor paints the image with its frame instead of a frame later); it cannot help an image whose
bytes have not arrived. React keys are per card `uid`, so a roll creates new card elements by design.

## The fix

- **One ordered pipe** (`assetQueue.ts`): 6 tasks in flight, strict lanes `now` → `chrome` → `early` → `set` →
  `audio` → `idle`, one fetch per key, raise-never-demote. Art (`artPreload.ts`) and the SFX bank (`sfx.ts`)
  both go through it, so audio no longer races the shop's art.
- **A plan** (`preloadPlan.ts`): boot queues the title screen chrome, the small UI icons, rank crests and mode
  tiles, then the shop chrome (board, card frames, tier stars, medallions, buttons, first milestone discs),
  then hand plates; then the live set's tier 1-2 cards, then heroes + powers; then the rest of the set, the
  other public art, skins, equipment, FX images; then (fetch-only, never decoded or held) other sets, runes,
  quests, Ancients. When a run exists, `preloadRunArt` queues the run's PINNED pool (`poolOf(run)`) tier-first,
  up to one tier past the tavern as `early`, re-planned only when set / tribes / tier change. Anything
  rendered-but-not-ready is raised to `now`.
- **Public-folder art is listed at build time** (`apps/web/publicArt.ts` → `__PUBLIC_ART__`): every image in
  `apps/web/public/` the UI source names, literally or through a template (`tier-stars-${tier}.webp`,
  `medallions/${id}.webp`). 145 of 156 files; dead boards and icons stay out.
- **Never show an undecoded image** (`useArtFade`, `FadeImg`): two checks, the URL (decoded by the pipe) and
  the ELEMENT (`img.complete`, read in a ref callback at commit, before paint). Not ready → invisible over a
  static dark portrait-shaped stand-in (`.art.art-wait`), then a one-shot 180 ms opacity fade. Ready → no class,
  renders exactly as before. Wired on the card art, frame, hand plate and every small chrome image on a card
  (tier plate + stars, medallion, milestone discs, gilded badge, text backbox, Epic medallion), hero select
  portraits, mode tiles, the lobby rail portraits, the rank crest and the title logo.
- **Netlify `_headers`** (`apps/web/public/_headers`, lands at the root of `dist/`): `/assets/*` (hashed)
  `public, max-age=31536000, immutable`; `/` and `/index.html` `no-cache`; unhashed public art (frames,
  medallions, cursors, fx, board images…) `max-age=3600, stale-while-revalidate=604800` so an edited frame still
  reaches players. `npm run release:web` refuses a build without it.

**Cost**

- Main thread: 0 long tasks and worst frame 4 ms on the title while the pipe is at full tilt (same as before);
  in an idle shop during preloading the worst frame was 21 ms vs 96-117 ms before (a late image landing). The
  one long task at shop open (~200-300 ms, cold only) is the Pixi WebGL context creation + an FX shape bake,
  present in both builds; a CPU profile of that window shows no measurable time in the preload code.
- Memory (renderer, after 150 s and a forced GC): before 791 MB working set / 726 MB private; after 793-861 /
  733-793. The first version held every image in the bundle as a decoded Image and cost ~250 MB more: that is
  why the `idle` lane only fetches.
- Bytes: a full session now pulls the whole bundle in the background (~115 MB over ~170 s at 10 Mbps, vs ~64 MB
  before, which never fetched spells, frames, runes…). The order means none of it delays what is on screen.
  With `_headers` a returning visit re-downloads nothing.

## Not done / follow-ups

- **Art file size** (separate, measured suggestion, no art touched): card art is 512×512 webp, ~63 KB average,
  displayed at ~184×237 CSS px in the shop at 1080p (larger on 4K and in Inspect). Re-encoding at 512 px
  quality 75 averaged 37 KB (-41%) and at 384 px quality 82 averaged 31 KB (-51%) on a 40-card sample. Worth an
  owner eyeball on a 4K screen before doing it.
- **Pixi/WebGL textures:** FX images and shapes were already decoded ahead by their libraries
  (`initImageLibrary` / `initShapeLibrary`) and the shader links pre-warmed (docs/performance.md §3b); their
  files are now also in the pipe's `set` lane. GPU texture upload on first use was not changed; it is a hitch
  risk, not a missing-art one, and wants its own measurement.
- **Decoded-image eviction in long sessions:** Chrome discards decoded pixels of off-screen images under its
  decode-cache budget; `decoding="sync"` makes a re-shown image decode inside the paint (no blank frame, a
  raster cost). Holding Image objects keeps the ENCODED bytes (no refetch), not decoded pixels, by design.
- **itch.io** ignores `_headers` (and the zip is already over itch's 1,000-file cap, unrelated).
- No oracle rule: the rules registry has no presentation domain (it holds gameplay rules).

## Owner action (Netlify)

Nothing to configure: Netlify reads `_headers` from the root of the uploaded folder, and it ships inside the
build. Deploy the next `npm run release:web` zip as usual. To check after deploying:
`curl -sI https://<site>/assets/<any hashed file>` should show `cache-control: public, max-age=31536000, immutable`,
and `curl -sI https://<site>/` should show `cache-control: no-cache`.
